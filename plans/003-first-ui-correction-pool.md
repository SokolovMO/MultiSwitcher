## p0.1 — постоянная иконка multiswitcher

**Причина, подтверждена.** В `DesignSystem.swift:97–104` `DesignIcon.currentBadge` читает системную раскладку; `application()` использует тот же `mark()` (`:135`). В `AppDelegate.swift:2155–2157` смена badge вызывает `DesignTheme.updateIcon()`, который присваивает `NSApp.applicationIconImage` (`DesignSystem.swift:86–88`). Поэтому Dock программно меняет знак на AZ. Runtime-отрисовка и SVG/ICNS имеют разные параметры, что даёт разные варианты знака в поверхностях.

**Дополнительная ошибка упаковки, подтверждена.** В исходном и установленном Info.plist указан `CFBundleIconName=AppIcon`, но `macos/Assets.xcassets` содержит только `AccentColor`; `assetutil --info` установленного `Assets.car` тоже показывает только этот цвет. SHA-256 исходного и установленного `MultiSwitcher.icns` совпадает. Custom-icon xattr на установленном bundle не обнаружен. Кэш macOS как причина различий пока не доказан; он не объясняет явный вызов обновления Dock при смене языка.

**Файлы:** `MultiSwitcher/macos/Sources/MultiSwitcher/{DesignSystem.swift,AppDelegate.swift,StatusPopoverController.swift}`, `macos/{Info.plist,generate_icon.swift,build_app.sh,MultiSwitcher.icns,MultiSwitcher-dark.icns}`, `macos/icons/app-icon*.svg`, `macos/Assets.xcassets`; общий `MultiDesignKit.swift` для brand mark в sidebar. Все пути относительно указанного выше корня соответствующего проекта.

**План:**

1. Зафиксировать постоянный мастер АЯ по эталону Dock 02/11: светлая плитка, пропорции и начертание. Не брать текущий Finder-вариант автоматически за эталон. Существующую runtime-отрисовку русского варианта использовать для сопоставления; экспортировать её с явным постоянным знаком и исключить зависимость от текущего языка.
2. Разделить API постоянного brand icon и динамического layout badge. Постоянный знак не читает TIS, не меняется при паузе, раскладке или смене темы. Внутренний знак в header/sidebar/help использует этот же мастер; адаптация окружения не меняет рисунок знака.
3. Генерировать ICNS и все размеры AppIcon из одного мастера. Добавить настоящий `AppIcon.appiconset`, согласовать его имя с Info.plist и сборкой. Проверить и fallback ICNS без actool. Не оставлять AZ/disabled-ресурсы альтернативными иконками приложения; сначала проверить их потребителей.
4. Убрать вызов смены applicationIcon из layout-пути; динамическими остаются только трей, меню раскладок и существующий индикатор каретки.
5. Проверить готовый bundle через Info.plist, assetutil, извлечение ICNS и подпись. Сначала проверить свежую тестовую копию. Если после исправления bundle останется доказанный stale cache — отдельно диагностировать его; глобальная очистка кэшей, перезапуск Dock/Finder и переустановка не входят в автоматические действия.

**Приёмка:** Finder, Dock, настройки, header трея, справка и «о приложении» используют одинаковый мастер АЯ в обоих оформлениях; запуск на английской раскладке тоже показывает АЯ. 30 смен RU/EN и проверка дополнительных установленных раскладок не меняют brand icon; трей продолжает показывать правильную раскладку. Ассеты покрывают 16–1024 px, без визуального изменения пропорций. Запись вызовов не показывает applicationIcon-обновлений из-за раскладки.

## p0.2 — живое состояние раскладки

**Причина, подтверждена.** `AppDelegate.systemInputSourceChanged()` (`:1862`) вызывает только `updateStatusIcon()`. Обновление заголовка и галочек NSMenu происходит в `menuWillOpen()` (`:1992–1997`). `StatusPopoverController.item()` превращает title/state NSMenuItem в новые значения `MultiPopoverItem`; уже показанные строки не наблюдают исходный NSMenuItem. `refresh()` существует, но layout-событие его не вызывает; в подменю он не получает новый root. Дополнительно `DesignIcon.currentBadge` и `badgeForCurrentLayout()` независимо вычисляют badge и по-разному обрабатывают нерусские языки.

**Файлы:** `MultiSwitcher/macos/Sources/MultiSwitcher/{AppDelegate.swift,StatusPopoverController.swift,DesignSystem.swift,LayoutSwitcher.swift,CaretIndicator.swift}`; общая строка в `MultiPopoverKit.swift`, только если нужен адресный update. Тесты — существующие Core/UI harness с новой проверкой интеграции уведомления и представлений.

**План:** один MainActor UI-store получает выбранный source ID, язык и список источников от существующего LayoutSwitcher. Badge — производное одного snapshot, не отдельный кэш у каждого view. Системное уведомление и успешные существующие пути выбора раскладки обновляют snapshot; fallback-опрос остаётся лишь восстановительным механизмом. Store не выбирает раскладку и не вмешивается в механизм конверсии. Состояние подписывают трей, tooltip/accessibility, строка раскладки, галочки открытого подменю и badge-provider каретки. Сохранять страницу меню, скролл и фокус; не пересоздавать всё меню ради буквы. Готовность/пауза по-прежнему читаются из существующих settings, без второго хранилища настроек. Сравнивать ID источника, а не только badge: две английские раскладки имеют одинаковый AZ.

**Приёмка:** с открытым root и подменю системный shortcut, globe, выбор раскладки из приложения и существующая автоконверсия обновляют все отображаемые значения без переоткрытия. Проверить RU/EN, две раскладки одного языка, дополнительный язык и добавление/удаление источника. В контролируемом тесте отображение меняется в ближайшем UI update после уведомления, целевой предел 100 ms; не ждёт таймера 2 s. Галочка всегда принадлежит одному source ID; фокус остаётся на прежнем действии. Dock при этом неизменен.

## p1.3 — sidebar меняет ширину окна

**Причина, подтверждена.** Общий `MultiSidebarHost.setCollapsed()` (`MultiDesignKit.swift:245–266`) анимирует только progress; `arrange()` (`:282–294`) отдаёт освободившиеся 148 pt detail-панели. Внешний NSWindow не изменяется, прежняя развёрнутая ширина не запоминается. Старый probe (`:550–553`) прямо требует неизменности frame при collapse. Это прежний контракт, который новый запрос заменяет.

Текущий фрагмент:

```swift
detail.frame = NSRect(x: width + 1, y: 0,
    width: max(0, bounds.width - width - 1), height: bounds.height)
```

**Файлы:** оба `MultiDesignKit.swift`, оба Core metrics; `MultiSwitcher/.../SettingsWindowController.swift:523–543,688–713`; `MultiShift/.../NativeViews.swift:193`, `MultiShift/.../AppDelegate.swift:649–714`; оба `MULTI_ECOSYSTEM_SPEC.md`; существующие SidebarChecks и geometry XCTest.

**План:**

1. Расширить существующую `MultiWindowPolicy` общим координатором геометрии. Одна фаза владеет шириной окна и rail; detail сохраняет полезную ширину. Не добавлять второй таймер поверх анимации host.
2. Для ручного collapse: rail 208→60, ширина окна уменьшается на 148 pt, высота сохраняется. Обычно сохранять верхний левый угол. Запомнить ширину развёрнутого окна до перехода; expand восстанавливает её без накопления погрешности.
3. Если пользователь сам меняет ширину компактного окна, пересчитать парную развёрнутую ширину как compact+148; при expand использовать последнее пользовательское решение. При переносе на меньший экран clamp имеет приоритет, но не должен портить запомненную желаемую ширину для возврата на большой экран.
4. Отделить ручной toggle от автоматического compact из-за узкого экрана: автоматический reflow не должен ещё раз уменьшать окно и запускать петлю hysteresis. Во время согласованного resize делегаты не переопределяют целевой frame и не сохраняют промежуточный autosave на каждом кадре; сохранить завершённую геометрию.
5. При быстром развороте начать из фактической текущей фазы; незавершённый collapse не подменяет сохранённый expanded frame. Обновить старое QA-условие неизменного frame на проверку delta и полезной ширины.

**Motion target:** номинально 260 ms, монотонная критически затухающая кривая без overshoot; использовать существующую формулу `(1-(1+9*t)*exp(-9*t))/(1-10*exp(-9))` как базовый профиль и один источник progress. При прерывании сохранять текущую геометрию; проверить непрерывность скорости и при необходимости продолжать из текущей скорости в том же координаторе. Reduce Motion — сразу итоговый frame. Нативный resize неизбежно требует layout; правило веб-анимаций «только transform» здесь неприменимо.

**Приёмка:** 20 циклов из normal/min/max, 40 быстрых разворотов, resize во время анимации. Без screen clamp итоговая delta ровно 148 pt, ширина detail и высота окна сохраняются с допуском 1 pt; после полного цикла исходная ширина возвращается с допуском 1 pt, дрейфа нет. Иконки, выбор и текст остаются в своих слотах на промежуточных кадрах. Одна активная анимация, ноль таймеров после завершения; одинаковое поведение в обоих приложениях.

## p2.5 — недавние операции multishift

- приоритет motion: HIGH; категории performance, interruptibility
- область: `MultiShift/macos/Sources/{StatusPopover.swift,AppDelegate.swift}`, оба `MultiPopoverKit.swift`, общий popover harness

**Установленные механизмы:** `StatusPopover.swift:55–68` переключает 1→20 строк и maximumBodyHeight 360→250. `MultiPopoverKit.swift:175–208` удаляет все body/footer views, создаёт их заново, меняет frame и сбрасывает скролл. Controller откладывает применение размера до следующего main-loop turn (`StatusPopover.swift:23–36`); затем resize closure присваивает `NSPopover.contentSize` (`AppDelegate.swift:223`). При этом `MultiPopoverKit.swift:171–173,217–224` делает синхронный bitmap snapshot и 160 ms crossfade только body. Старый bitmap помещается в новый viewport. Любой `model.objectWillChange` вызывает полный refresh (`StatusPopover.swift:39–43`), который сбрасывает текущий overlay и анимацию.

**Гипотезы по убыванию приоритета:** разрыв на один UI turn между layout и native размером; прерывание crossfade общим model refresh; затраты snapshot/создания строк на main thread. Код подтверждает наличие механизмов, но не их вклад в наблюдаемый рывок.

**План:**

1. На тестовой копии записать размеры popover/body/footer и timestamps в процессе раскрытия, а не только через 450 ms после него. Воспроизводить с 0/1/20 операциями и длинными именами, отдельно без model update и с update в середине перехода. Сопоставить main-thread trace и видео.
2. Оставить один расчёт целевой компоновки и одного владельца применения native contentSize. Согласовать frame body/footer и размер popover в одной управляемой транзакции; не накладывать отдельную анимацию открытия на системную.
3. Стабилизировать identity строк по operation ID; общие действия — по постоянному UI ID. Перестраивать только изменённые строки; сохранять скролл/фокус, пока пользователь явно не меняет страницу. Coalesce и сравнивать только snapshot данных, которые отображает меню.
4. Задать общий верхний предел viewport 250 pt для истории и вычислять высоту по содержимому/экрану; убрать смену конкурирующих 360/250 при toggle. Если popover должен вырасти, сделать один монотонный resize 200 ms ease-out `(0.23,1,0.32,1)`; body opacity — 160 ms той же кривой, с общим началом и без промежуточного пустого кадра. В Reduce Motion размер меняется сразу, движение отключено.
5. При прерывании брать текущую отображаемую геометрию, не перескакивать к началу. Generation guard для stale completion сохранить. Проверить вариант без bitmap snapshot; оставить snapshot только при измеренной необходимости и правильной геометрии.

**Приёмка:** 20 обычных и 40 быстрых toggle, приход операции во время перехода, скролл до середины списка, клавиши и Escape, обе темы, Reduce Motion. Ширина 340 pt неизменна; header закреплён; footer/body не расходятся; число resize соответствует выбранной транзакции, после завершения нет overlay/таймера. На 60 Hz нет зависаний главного потока >50 ms в переходе; оценить p95 интервала кадров относительно 16.7 ms на контрольной машине. Числа — критерии будущего измерения, не текущий результат.

- приоритет motion: MEDIUM; категории cohesion, accessibility, interruptibility
- область: оба metrics, оба `MultiDesignKit.swift`/`MultiPopoverKit.swift`; `MultiSwitcher/.../{SettingsWindowController.swift,DesignSystem.swift}`; `MultiShift/.../{NativeViews.swift,DesignSystem.swift,StatusPopover.swift}`

**Причина.** Sidebar уже общий, но timing остальных переходов разнесён: popover hardcode 0.16 с custom ease-out; Switcher section fade 0.07+0.09 с системным easeOut (`SettingsWindowController.swift:248–251,849–862`); Shift немедленно меняет ветку section (`NativeViews.swift:170–180`). В Shift есть отдельные Mono.spring/sidebarMotion; общий navigationDuration/hoverDuration ещё не определяет все фактические переходы. Нельзя считать все существующие анимации плохими: generation cleanup, Reduce Motion и клавиатурное исключение в popover уже есть.

**План / точные цели:** централизовать существующие токены и мосты AppKit/SwiftUI в MultiDesignKit; не добавлять motion-библиотеку. Навигация pointer: 160 ms opacity ease-out `(0.23,1,0.32,1)`; resize истории: 200 ms той же кривой; sidebar: профиль 260 ms из p1.3. Hover, если нужен переход цвета, 120 ms, без масштабирования; частые клавиатурные переходы — немедленно. В root↔submenu сохранять frame, когда содержимое помещается; длинное подменю скроллится. Между разделами — краткий transition только detail, без потери selection или нескольких наложенных живых страниц. Не анимировать весь AppModel, каждое progress-событие или смену раскладки. Reduce Motion: геометрия сразу, максимум 100 ms opacity для смены раздела; системные контекстные меню и NSPopover open/close оставляются нативными. Контроль input modality унифицировать между приложениями.

**Приёмка:** одинаковые переходы туда/обратно и быстрое повторное действие; никакого ожидания анимации перед кликом. Tab/Shift+Tab, стрелки, Enter/Escape, VoiceOver labels работают; переход темы не меняет геометрию. На замедленной записи нет скачка в начале/конце, вспышки старого контента или двойного футера. После закрытия окна не остаются анимационные таймеры. Проверить обычный motion и системный Reduce Motion.

## p3.7 — новая справка multiswitcher

## Финальная проверка и граница завершения

Перед реализацией сохранить baseline diff обоих уже грязных деревьев и точный source fingerprint, не сбрасывать и не коммитить чужие изменения автоматически. Проверки выполнять с изолированными preferences/profile, fixture-history и временными файлами. Существующие review hooks требуют проверки изоляции до запуска: например, AppModel может вызывать saveSettings при изменении языка. Функциональные сценарии проводить в тестовых TextEdit/файлах, не в текущих документах пользователя.

Для Switcher использовать `MULTISWITCHER_BUILD_ROOT`; для Shift — `MULTISHIFT_OUTPUT_DIR` и `MULTISHIFT_BUILD_CACHE_DIR`. Регрессии: ручная/автоматическая конверсия и undo в Switcher, выбор раскладки, правила/исключения/обучение без редактирования пользовательских наборов; Shift — конверсия временного файла, открытие результата/деталей, undo на fixture. Успех Core-тестов не заменяет эти UI-проверки.

Расширить существующие checks, а не создавать параллельный UI harness: outer frame delta/restore; pipeline source notification→открытый popover; история с live update и промежуточными кадрами; постоянство brand icon.
