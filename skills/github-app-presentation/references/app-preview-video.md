# короткое видеопревью приложения

Рецепт из принятого пользователем ролика MultiSwitcher. Применять к запросам демо,
превью и их правкам, а не к каждому изменению README. Это предпочтения для роликов
пользователя; явный новый бриф имеет приоритет. Не переносить функции одного продукта
в другой. Не перестраивать принятый ролик целиком ради небольшой правки.

## от кода к пользе

Прочитать README, инструкции проекта и код показанных действий: обработчики клавиш,
меню, состояние, результат, ограничения. Найти настоящие скриншоты, значки, шрифты
и исходные звуки. Отделить реализованное поведение от планов. Не добавлять в видео
неподтверждённые обещания о скорости, безопасности, форматах или разрешениях.

Сформулировать человеческую пользу одной фразой: какую рутинную работу человек
перестаёт делать. Показать её действием, а не списком функций. Например, у MultiSwitcher
ошибка раскладки → нажатие option → исправленный текст → человек продолжает мысль.
Для MultiShift заново найти его собственный сценарий в коде; не копировать текстовый
сюжет и горячую клавишу MultiSwitcher по аналогии.

## стиль по умолчанию

- 10–15 секунд; для принятой версии использовались 10 секунд, 1920×1080, 60 fps.
- Весь редакционный текст в кадре строчными: заголовки, набранный пример, подписи,
  названия клавиш и адрес `sokolovmo/имя-репозитория`. Не менять ради этого реальный
  регистрозависимый URL или команду. Если настоящие UI-пиксели содержат заглавные,
  выбрать честный кроп или аккуратно заменить только подпись; не менять сам продукт.
- Чистый белый фон `#ffffff` у светлых сцен, графитовый текст. Не тёплый кремовый фон.
  Контрастная тёмная сцена допустима, если помогает сюжету. Сохранить принятый контраст
  при небольшой правке светлых сцен.
- Стоковые macOS-шрифты и шрифты, подтверждённые кодом приложения. Для React подходит
  `-apple-system, BlinkMacSystemFont, "SF Pro Display", "SF Pro Text", sans-serif`.
  Без Fontshare, Google Fonts и загрузки сторонних веб-шрифтов для этого стиля.
- Настоящие интерфейс, меню строки macOS и иконки приложения. Не придумывать меню,
  элементы и декоративную панель управления. React-макет точно повторяет геометрию,
  отступы, состояние и типографику исходного UI. Синтетические данные без личной информации.
- Быстрая динамика: короткие пружины, резкие смены сцен, один ясно читаемый акцент
  за раз. Без долгих вступлений, пустых пауз, постоянной тряски и наложения крупных титров.

Для проверки нативного интерфейса использовать `apple-native-app-design`; он помогает
с точностью macOS, а не задаёт оформление маркетинговой страницы.

## раскадровка и реализация

Рабочая схема на 10 секунд, адаптировать к продукту:

- 0–1,4: сразу показать знакомую проблему на настоящем примере.
- 1,4–3,5: одно действие решает её; виден результат и продолжение работы.
- 3,5–5,5: реальное меню из строки macOS, один полезный переключатель.
- 5,5–7: второй короткий сценарий, только если он усиливает главную пользу.
- 7–8: одна подтверждённая особенность продукта, без общего рекламного обещания.
- 8–10: имя приложения, короткая польза и рабочий адрес репозитория.

Использовать React + TypeScript + Remotion; читать нужные разделы
`remotion-best-practices` для создания, markup, Studio и экспорта.
Открыть Studio при работе над сценой. Рендерить при поручении экспорта/публикации
или обновлении уже опубликованного ролика. Не считать простой запрос идеи разрешением
на публикацию. Визуальные анимации детерминированы кадром, без `Math.random()` на рендере,
CSS-таймеров и зависимости от реального времени.

Один файл таймингов: fps, длительность, кадры нажатий, исправления, открытия меню,
переходов. Из него строятся и визуальные события, и звуковые cues. Для резкой пружины
стартовая точка: stiffness 720, damping 17, mass 0.42, 12–16 кадров при 60 fps.
Это ориентир принятого ролика, не обязательные числа для каждой сцены.

Печатать не равномерной выдачей символов: детерминированный список кадров с разными
интервалами, маленькими паузами между группами и мигающей кареткой. Учитывать пробелы
в списке клавиш и синхронизации. После исправления человек продолжает ввод, показывая
непрерывность работы. Проверять строку целиком: плотный отрицательный tracking может
визуально съесть пробел после запятой. В принятой сцене помогли неразрывный пробел
и небольшое `wordSpacing`; проверить результат на готовом кадре, не только в строке кода.

## реальные звуки и «слух»

Сначала проверить аудио в проекте и доступные записанные библиотеки. Использовать
`real-sfx` для выбора записей, монтажа и cue-таймингов, `earshot` для анализа звука.
Наличие SKILL.md не доказывает наличие runtime: проверить установленный CLI/venv/MCP
и `earshot doctor`. Временные пути старой сессии не считать постоянной установкой.

Для недостающих записей — `openverse` с настроенным OAuth; секреты только из окружения.
Если его нет, не зацикливаться на настройке и не подменять API анонимным запросом:
продолжить независимый поиск открытых записей, например на Freesound, с проверкой
страницы автора и лицензии. Сохранить название, автора, исходный URL, лицензию и нужную
атрибуцию локально; обязательную публичную атрибуцию включить в готовую публикацию.
CC0 упрощает распространение. Лицензия на запись не следует из доступности MP3.

Палитра принятого ролика:

- Реальная низкопрофильная ножничная клавиатура, как MacBook, без механического thock.
  Несколько разных чистых ударов из одной записи, короткие fade, без обрезания атаки.
- Более выраженный тактильный щелчок на option, только если такая клавиша есть в сценарии.
- Лёгкие короткие swoosh и UI-click на появление меню и выбор. Не тяжёлый удар на каждый cut.
- Без обязательной музыки, голоса и синтезированных замен реальным записям.

Проверенный источник прошлой сцены: Plummet, “Low profile scissor keyboard”,
https://freesound.org/people/Plummet/sounds/749425/ (использовался как CC0;
перед повторным распространением проверить страницу). Это кандидат, а не доказательство
того, что всякая клавиатурная запись подходит на слух.

Каждую атаку ставить на кадр визуального события, учитывая тишину перед атакой
в исходном файле. Для печати и нажатия целиться в отклонение не больше одного кадра.
Не добавлять второй SFX поверх уже встроенного master. Сохранить отдельно локальные
cue-sheet и WAV-master, чтобы правки оставались воспроизводимыми.

Проверять финальный MP4 после AAC-кодирования: наличие дорожки, атаки, синхронизацию,
клиппинг и true peak. Держать запас, ориентир ≤ −1 dBTP; не повышать громкость ради
попадания в абстрактный LUFS. `earshot measure` даёт измерения; семантические методы
rank/find/describe/realness и timeline/sheet применять по необходимости и наличию моделей.
Измерения уровня и waveform не являются прослушиванием и не доказывают тембр клавиатуры.
Если модели недоступны, прямо указать границу проверки; не писать «послушал» или «звучит
идеально» по одному ffprobe/анализу волны. Не скачивать большие модели без необходимости.

## готовые файлы и публикация

По умолчанию производственный проект локальный: React-сцена, prompts, исходные записи,
WAV, отчёты, кеши и промежуточные рендеры не входят в продуктовый Git. Для MultiSwitcher
они лежат в игнорируемом `/marketing/`; для нового проекта выбрать точечный ignored-путь,
не игнорировать чужую существующую работу. Сохранить локальные исходники после экспорта.

При поручении публикации коммитить только согласованные готовые assets и оформление:
MP4, постер, оптимизированное GIF-превью, ссылки/разметку и необходимые изменения
публикующего скрипта. Не удалять файлы из истории и не делать force-push ради исправления
состава коммита. Скилл как переиспользуемая инструкция может храниться в существующем
`skills/`; это отдельно от исходников конкретного ролика.

Для продуктовой страницы — H.264 MP4/yuv420p + AAC, нативный video с controls,
playsinline, preload=metadata и постером. Для README — компактный GIF со ссылкой на
полный ролик со звуком; не рассчитывать на inline video HTML в README. Перевести alt
и подпись для каждого README. Социальная карточка GitHub — другая настройка, не видео.

На существующем сервере заново проверить current/symlink, фактический reverse proxy,
путь сайта и хеш текущего index. Backup, проверка входящих файлов по хешам, атомарная
замена только нужных assets; index последним, если изменяется. Сохранить updater,
appcast, latest.json, установщик и остальные маршруты. Не ставить системный nginx,
не добавлять конкурирующий proxy, не перезапускать весь стек ради статических файлов.
Не публиковать шаблон index с нераскрытыми токенами вместо действующей страницы.
Если обычный релиз пересоздаёт сайт, включить готовые assets в его существующую сборку.

После рендера проверить ключевые кадры: до/после действия, завершённый текст,
меню, конец. Проверить 60 fps/разрешение/длительность, читаемость и шрифты.
После публикации — скачанный MP4 совпадает по хешу, MIME и Range корректны,
README действительно использует новый GIF, remote SHA совпадает с нужным коммитом.
Отличать проверенный export от браузера без поддержки декодирования и от человеческой
приёмки. Сохранить рабочую версию и возможность отката; в ответе дать ссылки на результат.
