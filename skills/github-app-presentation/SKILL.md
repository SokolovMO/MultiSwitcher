# Оформление GitHub-приложений

Сделать репозиторий понятной страницей продукта и удобным местом для разработки.
Сначала проверить факты о приложении, затем оформить и проверить опубликованный результат.

## Контекст и границы

Проверить инструкции проекта, состояние Git, точный owner/repo и default branch.
Сохранить посторонние изменения. Найти действующую страницу загрузки, требования,
лицензию, способ обновления, CI и настоящие скриншоты. Отличать исходники в GitHub,
GitHub Releases и самостоятельную раздачу. Не обещать нотарификацию, безопасность,
поддержку ОС или успешную приёмку по одному факту сборки.

Оформление само по себе не включает переписывание истории, смену лицензии,
изменение приватности, слияние dependency PR, выпуск бинарников или серверный деплой.
При запросе синхронизации существующих чатов использовать инструменты чатов и
разделить владение файлами; не создавать новый чат без просьбы пользователя.

## Язык и композиция

Для проектов пользователя по умолчанию `README.md` — русский, `README.en.md` —
английский. Уважать иной явно заданный язык. Вверху обоих файлов дать взаимные ссылки.
Если старые языковые пути уже опубликованы, оставить там короткую ссылку на новый файл
и сохранить нужные старые якоря, а не поддерживать дублирующиеся полные README.

Первая часть README: знак/название, конкретный пример пользы, несколько полезных
бейджей, ссылки Скачать / Установка / Помощь / Ошибка. Затем кратко: возможности,
реальный интерфейс, установка, обновления, конфиденциальность, сборка, участие,
лицензия и maintainer. Количество и порядок секций адаптировать к приложению.
Для семейства приложений использовать [references/multi-apps.md](references/multi-apps.md).
Для иных продуктов не навязывать им знак AЯ, macOS, Homebrew или палитру Multi.

Оставлять сложное troubleshooting в SUPPORT или существующей документации.
Сохранять важные предупреждения рядом с действием, которого они касаются.
Проверять точные команды установки; не добавлять привилегированные команды и
обходы защиты, которых нет в проверенной схеме проекта.

## Графика

Использовать существующий знак и реальные синтетические скриншоты. Для простой
типографической обложки подходит SVG; не подделывать интерфейс рисунком.
Через `<picture>` поддержать светлую и тёмную темы, обязательный `<img>` fallback
и содержательный alt. Проверить шрифты, кириллицу, читаемость и отсутствие обрезки.
Если важна точность шрифта, экспортировать текст в контуры или проверить его
отрисовку на целевой площадке. Сохранять редактируемые исходники.

Различать:
- README-обложка — файл, на который ссылается Markdown.
- Social preview — отдельная настройка GitHub: Settings → General → Social preview.
  Подготовить PNG/JPG/GIF 1280×640, менее 1 MB; проверить актуальные ограничения
  GitHub при необходимости. Коммит PNG не устанавливает Social preview.
  При наличии подходящего авторизованного browser-инструмента загрузить и проверить
  результат; иначе явно указать, что карточка только подготовлена, и дать точный путь.
  Просмотр карточки в Settings не доказывает обновление кеша Telegram/других сетей.

## Видеопревью приложения

Если задача — показать пользу приложения коротким роликом, сделать или поправить
демо, использовать [references/app-preview-video.md](references/app-preview-video.md).
В этом режиме сначала изучить код и настоящий интерфейс, затем показать конкретное
действие и результат. Сам запрос ролика не означает переоформление всего репозитория.
Публиковать готовое видео и превью только в пределах поручения; производственные
исходники и звуковые материалы по умолчанию оставлять локально.

## Публичные документы и настройки

Дополнить существующие README, CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, SUPPORT,
CHANGELOG, формы Issues, шаблон PR и CODEOWNERS там, где это полезно проекту.
Не заполнять чеклист пустыми обещаниями и не выдумывать частные контакты, SLA,
даты релизов или лицензию. Сохранять обязательные copyright и third-party notices.

Описание, homepage и topics должны отражать фактическое назначение приложения.
У форм должны существовать используемые labels. Ссылки на закрытые отчёты об
уязвимостях публиковать после проверки, что функция действительно включена.
Не менять branch protection и другие workflow/security-настройки лишь ради красоты.
Не создавать публичные обсуждения или сообщения третьим лицам без прямого поручения.

## Проверка и публикация

Использовать [scripts/check_readme_links.py](scripts/check_readme_links.py), например:

```sh
python3 /path/to/github-app-presentation/scripts/check_readme_links.py \
  --root /path/to/repo README.md README.en.md
```

Скрипт проверяет локальные пути и Markdown/HTML-якоря; не проверяет внешние URL.
Отдельно проверить действующие внешние ссылки и GFM-рендер, картинки, бейджи,
оба языка, обе темы и читаемость при узкой ширине. Documentation-only правки
не требуют полной пересборки приложения. Проверить `git diff --check` и состав коммита.

Если публикация входит в поручение, опубликовать с указанным автором проекта,
без вымышленных co-authors. Проверить remote SHA, открывающийся README и metadata.
Community profile — дополнительный индикатор наличия файлов, а не сертификат качества
или безопасности. В результате дать ссылки, SHA и честные оставшиеся ограничения.
